2. OBJECT MODEL (use exactly this)
----------------------------------
Create an operation:

    op = flowsheet.Operations.Add("<DisplayName>", "<TypeString>")

Create a material stream:

    st = flowsheet.MaterialStreams.Add("<DisplayName>")

Facts you must rely on:

  * `Operations.Add(name, TypeString)` is the only supported creation call.
    There is no `.Inlet`, `.Outlet`, `.Connect`, `.ConnectStream`, `.Attach`,
    `.Link` or `.Add(<typename-only>)` on the flowsheet or on an operation.
  * `Add` raises a COM error if that display name already exists in the
    collection. Add exactly one object per JSON entry.
  * HYSYS accepts spaces, `/`, `.`, commas and mixed case inside element
    names, so you may use the JSON `id` unchanged. Only strip characters that
    would break a Python string literal: double quote, backslash, tab,
    carriage return, newline.
  * The fluid package and components must already exist before units are
    added - the basis step above your region has already done that.

A tag that NAMES the equipment item outranks the id prefix and outranks the
number of streams hanging off the unit. `C-101A/B Recycle Gas Compressor` has

do not "simplify" a named exchanger, compressor, pump or column into a
`TankOp` / `MixerOp` / `TeeOp` because of a port count you disagree with - the
count is a sketch-reading artefact and the code corrects it downstream.

cooling medium on one side, and `HeatExOp` is the class with verified
`ShellSideFeed` / `ShellSideProduct` / `TubeSideFeed` / `TubeSideProduct`
ports. Emit `AirCoolerOp` / `CoolerOp` only when you are confident the sketch
shows an air-cooled or utility-cooled unit AND the unit is not a column
overhead condenser.
Synthetic units whose id starts with `MIXER_TO_` are auto-inserted combining
points: treat them as normal units and use their tag (`mixer` -> ["MixerOp"]).

generic HYSYS vessel, which is neutral: it can be configured later as a
separator or a storage drum. Never fall back to `PipeSeg`, `MixerOp` or
`TeeOp` for a unit that is not literally a pipe, a mixing point or a flow

back to `["TankOp"]` for a unit whose tags name a fired heater, a column or an
absorber: those rows exist above and MUST win.

WHY `flashtank` AND `sep3op`
----------------------------
HYSYS resolves the second argument of `Operations.Add` against its RUNTIME
class registry, not against the palette labels. The palette label "Separator"
(`SepOp`) is a display alias only and is NOT instantiable - it fails with
E_FAIL and no source or description. The genuine classes are:

| candidate you pass        | VisibleTypeName the flowsheet shows | products |
|---------------------------|--------------------------------------|----------|
| "flashtank"               | 'Separator'                          | 2        |
| "sep3op"                  | '3 Phase Separator'                  | 3        |
| "TankOp"                  | 'Tank'                               | 2        |

All three expose the same ports: `Feeds`, `VapourProduct`, `LiquidProduct`,
`HeavyLiquidProduct`. So `flashtank` is a strict improvement over `TankOp` for
any separation duty: same connectivity, correct symbol, correct name. Only fall
back to `TankOp` when the unit is genuinely a storage or surge vessel.

WHY `DynamicFiredHeaterOp`
--------------------------
`"FiredHeaterOp"`, `"FiredHeater"` and `"Fired Heater"` are all PALETTE LABELS
and all fail `Operations.Add`. The runtime class is `"DynamicFiredHeaterOp"`:

| candidate you pass        | VisibleTypeName the flowsheet shows | TypeName                  |
|---------------------------|--------------------------------------|---------------------------|
| "DynamicFiredHeaterOp"    | 'Fired Heater'                       | 'dynamicfiredheaterop'    |

A fired heater is a furnace with a radiant section, an optional convection
section, its own fuel-gas stream and its own flue-gas product - it is NOT a
`HeaterOp` (one `FeedStream`, one `ProductStream`) and NOT a `HeatExOp` (which
would need a hot-side process stream that a fired heater does not have). If a
sketch shows a fired heater, a process furnace or a cracking furnace, emit
`"DynamicFiredHeaterOp"`.

WHY `Distillation` AND NOT A SEPARATOR
--------------------------------------
`"Distillation"`, `"Absorber"`, `"ReboiledAbsorber"` and
`"RefluxedAbsorber"` are genuine, first-class HYSYS operations:

| candidate you pass        | VisibleTypeName the flowsheet shows |
|---------------------------|--------------------------------------|
| "Distillation"            | 'Distillation'                       |
| "Absorber"                | 'Absorber'                           |
| "ReboiledAbsorber"        | 'Reboiled Absorber'                  |
| "RefluxedAbsorber"        | 'Refluxed Absorber'                  |

(`"ShDistOp"` also creates a real 'Shortcut Column', but the Shortcut Column
exposes no feeds, no products and no duties over COM at all. A unit created as
one can never be wired into the flowsheet, so it is forbidden here.)

A distillation column is not a `flashtank`: a separator has one equilibrium
stage, a column has many, and the reproduction is judged on the unit symbols
the flowsheet shows. Emit the column class. It needs one extra call before it
can be wired - see `WHY A COLUMN NEEDS ONE EXTRA CALL` below - and the
configuration document tells the configuration step how to make that call.

INLET / OUTLET COUNT RULES
--------------------------
The table already knows every multi-port family, so in the normal case you do
nothing but follow it. These rules exist only to rescue a unit whose chosen
type cannot carry the topology it was given.

  * NEVER re-type a unit on the strength of its stream count alone if the type
    the table gave you is one of

        TankOp, flashtank, sep3op, TeeOp, FractOp, BalanceOp, StreamCutterOp,
        ConversionReactorOp, EquilibriumReactorOp, GibbsReactorOp,
        PFReactorOp, KineticReactorOp, MixerOp, DynamicFiredHeaterOp,
        Distillation, Absorber, ReboiledAbsorber, RefluxedAbsorber

    Every one of these accepts several feeds and/or several products natively.
    In particular a reactor with three feed streams is still a reactor - the
    feeds are the reactants, not a mixing point. Do not turn it into a mixer
    and do not turn it into a tank. A fired heater with a process feed plus a
    fuel-gas feed is still a fired heater. A column with a feed plus a reflux
    line is still a column.

  * Two or more inlets on a unit whose type is single-inlet (PumpOp, ValveOp,
    HeaterOp, CoolerOp, AirCoolerOp, Compressor, ExpandOp, PipeSeg, Recycle,
    StreamCutterOp, YieldReactorOp) -> use ["MixerOp"]. A joining point must
    collect its feeds.

  * Two or more outlets on a unit whose type is single-outlet (PumpOp, ValveOp,
    HeaterOp, CoolerOp, AirCoolerOp, Compressor, ExpandOp, PipeSeg, Recycle,
    PFReactorOp, YieldReactorOp) -> use ["flashtank", "TankOp"]. Those types
    expose one `ProductStream` port, so a second product assignment silently
    DISPLACES the first and the unit ends up with only one product attached. A
    separator with a vapour and a liquid product is exactly this case.

WHY A COLUMN NEEDS ONE EXTRA CALL
---------------------------------
A column passes `Operations.Add` and then reports `VisibleTypeName`
'Distillation', but its inlet collection `ColumnFeeds` and its product
properties (`TopVapourProduct`, `BtmLiquidProduct`, ...) stay unreachable until
the operation has LOADED a column template. The load is one call that takes
the template name:

    T-100 = flowsheet.Operations.Add("T-100", "Distillation")
    T-100.LoadColumnTemplate("distil")   # loads Main Tower + Condenser + Reboiler

`distil` is the `distil.col` template that ships with every HYSYS install, in
`<install dir>\Template\`. After it loads, the column has four real, named,
bindable product nozzles (`Q-Condenser`, `Ovhd Vapour`, `Distillate`, `Btms`)
and a `ColumnFeeds` collection - verified on HYSYS V15 (41.0), build 150842.

Do NOT use `CreateColumnTemplate()`: it produces a bare tower with seven
unnamed placeholder slots, no condenser and no reboiler, and every product
assigned to it is silently lost.

That single `LoadColumnTemplate("distil")` call is emitted by the
CONFIGURATION step, not by you - it needs the operation object, which only
exists at run time. You only have to emit the right type; the configuration
document carries the rest of the recipe (`ColumnFeeds.Add(...)`, the product
properties and `ColumnFlowsheet.EnergyStreams.Add(...)`).
